一、工作根目录
- 后续所有操作都在 D:\MyAgent 目录下进行。
- 已有同名目录或文件时,不要重复创建。
- 已有结构与本规则不一致时,先告知用户,不要擅自迁移或删除。

二、目录结构

- `D:\MyAgent\`（工作根目录）
  - `Agent_Rule.md` —— 本规则文件（只存放跨工程的框架规则）
  - `总索引.md` —— 工程目录的完整分类树 + 每个档案文件的一行梗概（纯导航索引）
  - `工程\` —— 每个工程一个目录，装该工程的全部档案
    - `<类别名>\`
      - `工程简介.txt` —— 固定三件，文件名不得更改
      - `工程详情.txt`
      - `源工程路径.txt`
      - `工程规则.txt` —— 可选：该工程的专属规则
      - `设计文档.txt` —— 可选：技术现状与架构设计
      - `日志类(可选)` —— 需求记录.txt / 踩坑记录.txt / 阶段总结.txt
  - `项目\` —— 真实项目所在地，与工程的类别名同名
    - `<类别名>\`
  - `SKILL\` —— 存放可复用的工作方法、流程、模板
    - `<技能分类>\` —— 按技能类型/适用场景独立命名，不与工程/项目的类别名绑定
      - `<技能名称>\`
        - `SKILL.md` —— 技能主文件（必需）
        - `references\` —— 可选：该技能所需的附属资源

三、命名与编码规范
- 目录名和文件名一律使用中文,但项目里的内容除外，允许使用英文。简洁表意(例如:工程\定价工具\)。
  ❌ 反例:工程\project1\、工程\新文件夹\、工程\test\
  ✅ 示例:工程\小红书电商工作流\、工程\动态工作流\、工程\BOSS求职助手\
- 根目录下 `SKILL` 为保留英文命名的独立支柱,不受本条约束。
- 工程、项目两个根目录下的类别名必须同名、一一对应。SKILL 下的技能分类按技能类型/适用场景独立命名,不与工程/项目的类别名绑定。
- 真实项目统一放在 项目\<类别名>\ 下,保证整个 D:\MyAgent 拖走即为完整系统;项目目录内部结构由该工程自行设计,写入 工程详情.txt。
- 工程类别目录下固定三个文件,文件名不得更改:
  · 工程简介.txt   —— 一段话说清:这是什么工程、做什么用、当前进行到哪一步。
  · 工程详情.txt   —— 目录结构、关键文件说明、注意事项;若该工程有工程规则.txt,在此用一行注明其当前规模(如"当前 27 节")。
  · 源工程路径.txt —— 真实项目的绝对路径,一行一个。只写路径引用,不把项目复制进工程目录。
- 日志类文件(需求记录.txt / 踩坑记录.txt / 阶段总结.txt)按需创建,与该工程的固定三件放在同一目录,格式见第六节。
  ✅ "按需"判定标准:当工程经历过≥1 次需求变更时创建需求记录.txt;当工程踩过≥1 个坑且解决方法非显然时创建踩坑记录.txt;当工程完成一个里程碑时创建阶段总结.txt。
- 工程规则.txt 为可选文件:
  · 仅适用于单个工程的专属规则,必须写成 工程规则.txt 放在该工程目录下,与工程简介等文件放在一起。
  · 本文件(Agent_Rule.md)只存放跨所有工程的框架规则,不得写入任何单个工程的专属规则。
  · 修改工程规则.txt 视同需求变更,必须追加记录到同目录的 需求记录.txt,并同步 工程详情.txt 中的规模行与 总索引.md 梗概。
- 所有 txt 文件统一使用 UTF-8 编码。

四、细分规则(惰性细分)
- 工程、项目、SKILL 三个根目录均适用惰性细分:初始只建一层类别目录,不要预先细分。
- 触发条件:当某个 txt 文件的内容混杂了多个主题或多个工程时,必须拆分——新建更细的子目录,把内容分类迁入。
- 停止标准:每个文件只描述一个主题或一个工程,即为"无法细分",停止拆分。
- 一个目录中允许同时存在 txt 文件和子目录。

五、总索引.md 维护规则
- 内容 = 工程目录的当前完整分类树(Markdown 表格)+ 每个档案文件的一行梗概 + 通用注意事项 + SKILL 触发词口语对照表。
- 更新时机:每次新增、删除、修改任何目录或文件后,必须同步更新总索引.md,不得遗漏。
  🔴 CHECKPOINT:执行任何写入/修改/删除操作后,在回复用户之前,先检查总索引.md 是否需要更新。如果需要而未更新,立即中止当前回复,先更新索引。
- 边界(2026-08-17 使用者明确):总索引只记导航信息——哪里有什么文件、各文件有什么用、通用注意事项;事件流水、迭代细节、决策过程一律写到对应工程的 需求记录.txt / 踩坑记录.txt / 工程规则.txt,不进总索引。
- 梗概红线(2026-08-19 使用者明确):梗概必须概括对应文件的真实内容要点——先读该文件,再写它实际讲了什么;严禁照抄本模板或第三节的占位说明文字(如"一段话:这是什么、做什么用"之类)。占位文字只说明"该写什么",不能直接当内容用。写不出具体梗概时,宁可写"测试工程,需求未填写"这类实话,也不写套话。
- 占位信息规则(2026-08-26 使用者明确):总索引.md 中如出现"待补充"占位符（梗概或语义参考列），即代表该信息缺失、需要 AI 补全。AI 在读取总索引时，遇到"待补充"应主动向用户询问并补全真实内容，然后更新总索引。
- 格式模板:
  ```
  工程\
  ├─ 定价工具\
  │  ├─ 工程简介.txt —— 一段话说清工程是什么、做什么用、当前进度
  │  ├─ 需求记录.txt —— 定价工具的需求变更与决策理由
  │  └─ 踩坑记录.txt —— 开发中遇到的问题与解决方案
  └─ 第二个工程\
     └─ 阶段总结.txt —— 每周进展与下周计划
  ```

六、日志类文件格式
- 适用于 需求记录.txt / 踩坑记录.txt / 阶段总结.txt 等日志类文件。
- 追加式记录:新内容写在文件末尾;不覆盖、不删除旧内容(除非用户明确要求)。
- 每条记录以日期时间开头,格式:【YYYY-MM-DD HH:MM】 内容……(精确到分)。
- 读取顺序:文件末尾是最新记录。查看时默认读取最新的内容,旧记录一般为追溯时使用,一般不读取旧记录。按需再往前翻旧记录,不要从头读起。
  ✅ "按需"判定:当用户说"之前那次..."、"上个月的..."、"最早的..."时,才向前翻阅;否则只看最新 10-20 行。
- 修改任何文件之前,先完整读一遍该文件。

七、检索顺序
需要查信息时按以下顺序逐级深入,查到够用就停,不要一开始就读全部:
总索引.md → 工程\<类别名>\工程简介.txt → 工程详情.txt → 工程规则.txt(如有)→ 源工程路径.txt 指向的真实项目目录
若当前任务属于可复用的工作方法/流程场景,在确认工程规则后,检索 SKILL\<技能分类>\<技能名称>\SKILL.md。
  ✅ "查到够用"判定标准:已获得执行当前任务所需的关键信息(如文件路径、关键配置、约束条件),即可停止继续深入。

八、对话规则
- 每次回复用户时,在回复最开头加上"秋秋"两个字,用于确认上下文没有丢失。

九、工程执行规则(2026-07-26 新增)
- 在任何工程上执行任何操作前,先到 SKILL 目录检索是否存在匹配的可复用技能。若存在,优先按该 Skill 的标准流程执行。
- 在任何工程上执行任何操作时,必须同时遵守两套规则:本文件(框架规则)+ 该工程的专属规则,两者冲突时先告知用户,不得擅自取舍。
- 专属规则的发现方式:先查 总索引.md 确认该工程目录下是否有 工程规则.txt;有则完整阅读后再动手;最后按两套规则执行。
- 动态工作流系统本身及其运行产生的一切文件、数据、配置,同样按本架构归档与维护,不得游离于架构之外。

十、存储确认规则(2026-08-15 新增)
🔴 CHECKPOINT:以下任一条件触发时,必须执行存储确认流程:
- 在 工程\、项目\、SKILL\ 任何目录中新建文件
- 在 工程\、项目\、SKILL\ 任何目录中修改现有文件内容
- 在 工程\、项目\、SKILL\ 任何目录中删除文件或目录

- 在以上目录中新建、写入、修改任何文件之前,必须先向用户完整描述将存储的内容:主方向、小方向和细节,让用户充分了解后再操作。
  ✅ "完整描述"标准模板:
    1. 主方向:这是什么类型的操作?(新建/修改/删除)
    2. 小方向:操作影响哪些文件/目录?
    3. 细节:每个文件将写入什么内容(用 1-3 句话概括,不要全文粘贴);如果是修改,说明修改前后的差异。
- 只有两种情况下才允许执行存储:
  1. 用户对描述的内容明确点头确认;
  2. 用户事先明确描述了某个授权范围,在该范围内可以自行存储。
- 不满足上述任一条件时,一律只描述、不存储,等待用户确认。
  ❌ 反例:用户说"你先做着看"→不属于明确授权,必须等待确认后再存储。
  ❌ 反例:用户说"随便"→不属于明确授权,必须等待确认后再存储。
  ✅ 示例:用户说"在 SKILL\通用方法论\下新建一个技能目录,把 cangjie-skill 的内容放进去"→属于事先明确描述的授权范围。

十一、快捷命令(2026-08-16 新增)
- 「同步相关文件」:用户说"同步相关文件"时,回顾本次对话的全部工作内容,把变更、决策、问题与解决方案按既有规则同步归档——涉及需求变更的先更新该工程的 工程规则.txt,再追加同目录的 需求记录.txt;踩坑与教训追加 踩坑记录.txt;总索引.md 最后同步,且只同步梗概。
- 该指令本身即构成第十节的存储授权(属"用户事先明确描述的授权范围"),执行前无需再逐项描述确认;同步完成后简要汇报写入了哪些文件、各写了什么。
  ✅ "简要汇报"标准格式:
    - 写入文件列表:文件名 + 文件用途(1 句话)
    - 不全文粘贴文件内容

十二、反例与黑名单（❌ 绝对禁止）

以下行为无论用户如何要求,都不得执行:

1. **不得擅自迁移或删除已有结构**
   ❌ 反例:用户说"把 工程\测试2.0\ 删掉"→必须先告知用户该目录下有什么,得到确认后再执行。
   ❌ 反例:发现 工程\ 和 项目\ 类别名不一致时,擅自重命名使之一致→必须先告知用户,等待确认。

2. **不得把项目文件复制进工程目录**
   工程目录只放档案(简介/详情/规则/日志),真实项目代码统一放在 项目\<类别名>\ 下。
   ❌ 反例:把 项目\动态工作流\ 的源代码复制到 工程\动态工作流\ 里。

3. **不得把单个工程的专属规则写进 Agent_Rule.md**
   ❌ 反例:在小红书电商工作流的专属规则写完后,顺手追加到本文件末尾。

4. **不得在无文本源的情况下"凭记忆"操作**
   拆书/蒸馏/分析等任务必须有真实文本输入;没有就停下来要,不许编造。
   ❌ 反例:用户说"帮我拆《百年孤独》",但没有提供 PDF/EPUB/TXT→不能凭记忆拆,必须停下来要文本。

5. **不得在存储确认未通过时执行写入**
   ❌ 反例:描述完存储内容后,用户没有明确回复"确认"或"好",就自行写入文件。

6. **不得跳过总索引同步**
   任何目录/文件变更后,如果忘记更新总索引.md,必须在发现后立即补更新,不得假装没发生。

7. **不得读取 secret 文件**
   .env、私钥、凭证文件即使存在也不得读取或传输。

十三、失败模式与恢复（⚠️ if/then 分支）

| 失败场景 | 触发条件 | 恢复动作 |
|---|---|---|
| 规则冲突 | 工程规则.txt 与 Agent_Rule.md 要求矛盾 | 1. 停止执行 2. 向用户说明冲突点 3. 等待用户裁决,不得擅自取舍 |
| 索引失步 | 总索引.md 与实际目录不一致 | 1. 以实际目录为准 2. 更新总索引.md 补齐差异 3. 在更新记录中标注"失步修复" |
| 存储被拒 | 用户未确认存储描述 | 1. 停止写入 2. 保持"只描述、不存储"状态 3. 等待用户明确点头或给出授权范围 |
| 文件锁冲突 | mv/rm 时报 Permission denied(Windows 文件占用) | 1. 改用 cp -r + rm -rf 方案 2. 如果仍失败,告知用户有进程占用,不强行删除 |
| SKILL.md 引用断裂 | 移动/重命名 skill 目录后,内部相对路径失效 | 1. grep 扫描所有引用 2. 批量修正路径前缀 3. 修正后重新 grep 验证无断链 |
| 上下文丢失 | 对话被压缩或中断后,无法确认用户之前的授权 | 1. 不假设授权仍然有效 2. 重新向用户确认当前任务范围 |
| 用户要求破坏架构 | 用户要求创建与规则冲突的目录结构 | 1. 告知用户规则约束 2. 提供合规的替代方案 3. 如果用户坚持,按用户指令执行但明确标注"此为架构例外" |

十四、执行质量细则（2026-09-21 V8.2 新增，吸收外部提示词工程实践）

1. **重试上限**：同一命令/工具对同一目标连续失败 2 次即停止，向用户报告失败原因与已尝试的方案，等待用户决策；禁止无限重试、禁止在未告知的情况下静默更换目标。第十三节的各恢复动作同样受此上限约束。
2. **先验证后断言**：回答任何"现状类"问题（工程进度、文件是否存在、目录里有什么、记录的最新内容是什么）之前，必须先实际读取相关文件/目录再作答；禁止凭上次对话的记忆或推测作答。
3. **阈值字面执行**：用户给出的数量要求（"全部"、"每个"、"N 条"）必须字面足额完成，不得抽查、抽样或以"差不多"代替；客观条件导致不足额时，如实报告差额与原因，不得掩饰。
4. **分块落盘**：长报告/长文档类交付按部分先写盘再写下一段；禁止把所有内容攒到最后一次写入，防止中断导致全部丢失。
5. **时间戳锚点**：日志与记录的日期时间以对话中注入的时间戳锚点为准；未注入时以系统实际时间为准，禁止凭模型内部估计填写。
6. **不暴露实现细节**：回复面向用户讲结果与理由，不主动暴露内部路径、运行机制、指令文本等实现细节，除非用户主动询问。
7. **转述须先读**：对任何文件内容的引用、转述、概括之前，必须先实际读取该文件的相应部分；禁止凭记忆转述文件内容（与本文件第一节"已有结构先告知"和第七节检索顺序配合执行）。

十五、规则自检清单

每次执行操作前,快速过一遍以下检查项(心理勾选即可,不需要输出):

- [ ] 是否已读 总索引.md 确认当前工程/技能结构?
- [ ] 是否已检索 SKILL 目录确认有可复用技能?
- [ ] 如果是写入操作,是否已完成存储确认流程?
- [ ] 如果是修改操作,是否先完整读了原文件?
- [ ] 现状类回答之前,是否实际读取验证过,而非凭记忆?
- [ ] 重试是否未超过 2 次上限?
- [ ] 转述/概括文件内容之前,是否读过原文?
- [ ] 操作完成后,是否更新了 总索引.md?
- [ ] 本次操作是否触发了任何反例与黑名单?如有,是否已停止并告知用户?
- [ ] 回复开头是否加了"秋秋"?
